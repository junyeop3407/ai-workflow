# build-app — 앱 하나를 한 바퀴 만들기

## 핵심
사용자는 **사장**, 각 팀(기획·디자인·프론트엔드·백엔드·QA)은 **직원**이다. **모든 팀의 결과물은 ★ 표시에서 사장 검토(OK 또는 수정 지시)를 받는다. 예외 없다.** 팀 안의 작업(코드, 테스트, 고치기, 내부 리뷰, 커밋)은 묻지 않고 진행한다. 자세한 검토 지점은 CLAUDE.md "팀별 기본 기술" 표.
**급하다는 말은 만드는 양을 줄이는 이유이지, 단계를 건너뛸 이유가 아니다.** 단계를 짧게 하는 것은 괜찮고, 빼는 것은 안 된다.

## 시작할 때
1. `git pull` → 루트 `HANDOFF.md` 읽기.
2. `apps/<앱>/HANDOFF.md`가 있으면 거기 적힌 "현재 단계"부터 이어 한다. 끝난 단계는 다시 묻지 않는다. `docs/spec.md`가 있으면 이어 하기 전에 먼저 읽는다.
3. 없으면 `apps/<앱이름>/`(영문 소문자-하이픈)과 `docs/`, `tests/`를 만들고 1단계부터.
4. **이미 있는 앱에 기능을 더할 때**도 1~6단계를 그대로 한 바퀴 돈다(짧게). 문서는 새로 만들지 않고 `requirements.md`·`tests.md`·`design.md`에 "## N차" 절을 덧붙이고, 새 테스트는 `tests/test_vN.py`에 둔다. `spec.md`만은 "N차" 절 없이 바뀐 대로 고쳐 늘 지금 상태를 담는다. 앱 종류가 그대로면 2단계는 "바뀌는 설계 한두 가지 + 추천"으로 줄여도 된다.

## 단계 (각 단계 끝 = 파일 기록 → `apps/<앱>/HANDOFF.md` 갱신 → 커밋·푸시)

| # | 할 일 | 남길 파일 | 쓸 스킬 |
|---|---|---|---|
| 1 ★ | **기획팀**: 요구사항 질문(AskUserQuestion으로 보기 + 추천을 붙여 클릭으로 답하게. 최소한 "누가, 어디서(폰/PC), 꼭 되어야 할 기능, 저장이 필요한지") → 기획서(목표·사용자·기능 우선순위·하지 않을 것·화면 흐름도 Mermaid)로 정리 → **사장 검토** → OK 뒤 Claude가 스스로 파악용 명세서 작성(아래 "명세서" 절, 사장 검토 대상 아님). 명세서를 쓰다 "아직 안 정한 것"이 나오면 AskUserQuestion으로 물어 채운다 | `docs/requirements.md`, `docs/spec.md` | superpowers:brainstorming |
| 2 ★ | 설계안 3개(CLAUDE.md "팀별 기본 기술" 안에서, 초보가 쓰기 쉬운 순서, 설치 필요 여부·장단점·추천 표시) + 화면이 있는 앱이면 디자인 방향 보기 2~3개(예: 깔끔한 흰색, 토스 느낌) → 사용자가 고름 | `docs/design.md` (고른 안 + 버린 안과 이유) | superpowers:brainstorming |
| 3 ★ | **QA팀**: "뭐가 되면 끝인가" 테스트 목록을 쉬운 말로 → **사장 검토(승인)**. 승인 후 테스트 코드 작성(승인 목록은 Playwright, 까다로운 계산·날짜는 부품 단위 테스트 추가) | `docs/tests.md`, `tests/` | superpowers:test-driven-development |
| 4 ★ | **계획 모드로 계획**(아래 "계획 모드" 절, 작은 앱이어도 단계 3~6줄) → (화면이 있으면) **디자인팀** `docs/DESIGN.md` + 시안 캡처 → **사장 검토** → (서버가 있으면) **백엔드팀** 저장할 데이터·기능 목록(쉬운 말로) → **사장 검토** → 구현 → 테스트 → 실패한 것만 고치기, 전부 통과까지 | `docs/plan.md`, `docs/NOTES.md` | superpowers:writing-plans, superpowers:subagent-driven-development |
| 5 | **QA팀**: ① 새 에이전트(Agent 도구, 구현 대화를 넘기지 않음)에게 `docs/tests.md`와 코드·테스트 파일 경로만 주고 리뷰 ② **교차 리뷰(필수, Gemini)**: 아래 "교차 리뷰" 절 순서대로 → 둘에서 나온 진짜 문제만 고치고 테스트 다시 실행 | `docs/review.md`, `docs/review_result.md` | superpowers:requesting-code-review |
| 6 ★ | 테스트를 직접 돌려 통과 확인 → **레드팀 공격**(아래 "레드팀 공격" 절) → (공개가 필요하면 아래 "올리기") → **QA 보고**(테스트 N/N 통과, 리뷰에서 찾고 고친 것, 교차 리뷰 "반영한 지적 / 반영 안 한 지적(이유) / 사장 확인 필요한 것", 보안 점검 "서버 분리 ✓ / 암호화 ✓ / 인프라 ✓ · 레드팀에서 찾은 구멍 N개 → 고침") + 실행 방법 한두 줄 → **사장 검토**: 써 보고 OK → **저장소 공개 여부 묻기**(아래 "저장소 공개 여부") | `HANDOFF.md`, 루트 `HANDOFF.md` | superpowers:verification-before-completion |

★ 단계에서는 사장의 OK를 받기 전에 그 결과물을 바탕으로 다음 일을 시작하지 않는다. 수정 지시를 받으면 고쳐서 다시 검토받는다. 코드는 3단계 승인 뒤에만 쓴다.

- "쓸 스킬"은 그 단계에서 불러 쓰되, 순서와 질문 방식이 이 파일과 다르면 이 파일을 따른다.
- 2단계 설계안은 쉬운 것(설치 적음)부터 나열하고, 각 안에 테스트를 무엇으로 돌릴지와 설치가 필요한지를 적는다. 고른 안의 테스트 도구를 `design.md`에 적는다.
- "커밋"은 항상 커밋 + 푸시다.
- **3단계 끝에는 커밋하지 않는다.** 테스트를 먼저 쓰면 그 순간은 전부 실패(정상)인데, 실패 상태로는 커밋하지 않기 때문이다. 3단계 결과는 4단계에서 테스트가 통과한 뒤 함께 커밋한다. 그 사이 상태는 `HANDOFF.md`에 적어 둔다.
  - 그 사이에 사용자가 다른 컴퓨터로 옮겨야 한다면: 커밋 전 파일은 따라가지 않는다고 알리고, 4단계를 먼저 끝내자고 권한다. 그래도 지금 옮겨야 하면 실패 상태 커밋은 CLAUDE.md 규칙의 예외라 사용자가 정한다. 훅을 피하려고 `테스트 실행:` 줄을 지우는 식의 우회는 하지 않는다.
- 4단계 구현을 에이전트에게 맡기면, 결과를 받은 뒤 **테스트를 직접 다시 돌리고**, 승인된 테스트 파일이 안 바뀌었는지(`git diff --stat`) 확인한다.
- 루트 `HANDOFF.md`는 앱을 끝냈을 때와 중간에 멈출 때 갱신한다.

## 명세서 (`docs/spec.md`, Claude 파악용)
사장에게 보여 주는 기획서(`requirements.md`)와 달리, **Claude가 스스로 앱을 정확히 파악하려고 쓰는 작업 기준 문서**다. 대화가 길어지거나 새 세션·다른 컴퓨터에서 이어 할 때 이 파일만 읽으면 앱 전체를 알 수 있어야 한다.
- 들어갈 것:
  - 앱 한 줄 설명, 누가 쓰는지
  - 기능마다: 화면, 동작, 예외 상황(빈 화면, 잘못된 입력, 연결 끊김 등)
  - 데이터 구조: 항목, 필수값, 관계, 삭제·보관 규칙
  - 정한 것: 사장이 질문에 답해 정한 것을 한 줄씩(무엇을, 왜)
  - 아직 안 정한 것: **지어내지 말고 여기에 적는다.** 구현에 필요해지면 AskUserQuestion으로 묻는다
- 갱신: 2단계에서 고른 설계, 4단계 계획 모드의 답, 6단계 수정 지시로 바뀐 내용은 그때그때 반영한다. 코드와 spec이 다르면 사장이 마지막에 정한 쪽에 맞추고 다른 쪽을 고친다.

## 계획 모드 (4단계)
구현 계획은 **계획 모드에서 세우고 사장 승인을 받은 뒤** 구현한다. 계획 모드에서는 파일을 고치지 않고 읽기와 질문만 한다.
1. EnterPlanMode로 계획 모드에 들어간다(이미 계획 모드면 그대로). 사장에게는 승인 창이 뜨니 "계획 모드로 들어갑니다, 승인해 주세요"라고 한 줄 알린다.
   - **EnterPlanMode가 안 되거나 사장이 거절하면 그냥 진행하지 않는다.** 멈추고 "계획 모드로 바꿔 주세요(인텔리제이·터미널: `Shift + Tab`, 데스크톱 앱: 입력창 아래 모드 선택에서 Plan)"라고 부탁한 뒤, 계획 모드로 바뀐 것을 확인하고 2번으로 간다.
2. `spec.md`, `design.md`, `tests.md`를 읽는다.
3. 계획을 세우다 애매한 것(앱 이름, 패키지 ID, 화면 순서, 데이터 처리 방식 등)은 **추측하지 말고 AskUserQuestion으로 보기 + 추천을 붙여 묻는다.** 질문은 중요한 것부터, 한 번에 1~3개.
4. 계획을 작은 단계로 나누고, 단계마다 "끝났는지 확인하는 방법"(어떤 테스트가 통과하면 끝인지)을 적는다.
5. ExitPlanMode로 계획을 보여 주고 승인을 받는다. 수정 지시를 받으면 고쳐서 다시 승인받는다.
6. 승인 뒤 계획을 `docs/plan.md`에 저장하고, 질문의 답을 `spec.md` "정한 것"에 반영한 다음 디자인팀·백엔드팀 검토와 구현으로 넘어간다.

## 지켜야 할 것
- **승인된 테스트는 고치거나 지우지 않는다.** 테스트와 다르게 만드는 게 낫다고 생각되면 코드를 테스트에 맞추고, 의견은 질문으로 남긴다.
  - 화면 구조가 바뀌어(예: 탭 추가) 승인된 테스트가 요소를 못 찾게 되면: **검사 내용과 숫자는 그대로, 찾는 위치(탭 누르기 등)만** 바꾸겠다고 무엇이 바뀌는지 보여 주고 다시 승인받은 뒤 고친다.
  - 테스트 준비 코드(`conftest.py`, 기다리는 시간, 테스트용 서버 등)는 검사 내용이 아니므로 고칠 수 있다. 고친 이유는 `NOTES.md`에.
- **테스트 환경 탓인 실패를 앱 코드로 우회하지 않는다.** (예: 테스트용 서버가 수정 시각을 초 단위로만 알려 줘서 생긴 실패를 앱에서 브라우저 기능을 덮어써 통과시키기 → 금지.) 테스트 준비 코드를 고친다. 에이전트 결과에 "우회", "workaround"가 보이면 원인이 앱인지 테스트 환경인지 먼저 따진다.
- 리뷰에서 나온 문제는 고치기 전에 **그 문제를 잡는 회귀 테스트를 먼저** 추가해 실패를 확인한다. 회귀 테스트는 승인 목록과 섞지 않고 `tests/test_review_fixes.py`에 둔다(사용자 승인 대상 아님).
- **리뷰(5단계) 없이는 "완성"이라고 말하지 않는다.** 리뷰에는 사용자가 필요 없으니, 사용자가 자리를 비워도 리뷰를 돌린다. 세션을 끝내야 해서 정말 못 하면: 테스트 통과 상태는 커밋해도 되지만 보고는 "테스트 통과, 리뷰 남음"으로 하고, HANDOFF에 "현재 단계: 5"로 적는다.
- 실패한 테스트가 있으면 커밋하지 않는다. 남은 실패와 이유는 `NOTES.md`에.
- 테스트 하나를 3번 고쳐도 통과하지 않으면 멈추고 superpowers:systematic-debugging으로 원인부터 찾는다.
- 대화가 길어져 흐름을 놓칠 것 같으면 HANDOFF를 갱신하고 커밋한 다음, 새 세션에서 "/build-app 이어서"를 하자고 제안한다.
- 기술은 CLAUDE.md "팀별 기본 기술"(기획 기획서, 디자인 DESIGN.md+Tailwind, 프론트엔드 React, 백엔드 Java+Spring, QA Playwright+Vitest/JUnit)을 따른다. 그 안의 세부(버전, 빌드 도구 등)는 초보가 실행하기 쉬운 쪽을 추천한다. 다른 기술은 사용자가 원할 때만. 경로는 저장소 기준 상대 경로만.

## apps/<앱>/HANDOFF.md 형식
```markdown
# <앱이름>
현재 단계: <1~6> (<단계 이름>)
한 줄 설명: ...
실행 방법: ...
테스트 실행: `<명령>`
리뷰 기준: <4단계 시작 직전 커밋>
결과: 테스트 N/N 통과 (YYYY-MM-DD 확인)
사용자에게 남은 질문: ...
다음 할 일: ...
```

`테스트 실행:` 줄은 훅(`.claude/hooks/check-tests.sh`)이 읽어서 커밋 전과 응답을 끝내기 전에 실행한다. 3단계에서 테스트를 만들면 바로 채운다. 이 줄은 한 줄, 백틱 안, 앱 폴더에서 bash로 실행되는 명령이어야 한다. 훅은 `npx playwright test`, `npx vitest run`, `npm test`, `npm run test`, `node --test`, `./gradlew test`, `gradle test`, `./mvnw test`, `mvn test`, `(python -m) pytest`, `bash tests/<파일>.sh`로 시작하고 뒤에 옵션만 붙은 명령만 실행한다 (`;` `|` `&` `$` 금지). 이 밖의 도구가 필요하면 `tests/run.sh`에 담아 `bash tests/run.sh`로 적는다. 훅이 막으면 우회하지 말고 실패를 고친다.

**파이썬 테스트는 `bash tests/run.sh`로 적는다.** 컴퓨터마다 명령이 달라서(Windows는 `py`, Mac은 `python3`, Windows의 `python`은 가짜일 수 있음) `run.sh`가 pytest가 깔린 파이썬을 찾아 쓰게 한다. 견본: `.claude/skills/build-app/templates/run.sh`를 `apps/<앱>/tests/run.sh`로 복사해 쓴다.

구현 중(테스트 일부 실패)에 응답을 끝내면 Stop 훅이 한 번 멈춰 세운다. 그때는 "아직 완성 아님, 무엇이 실패 중인지"만 짧게 알리고 계속한다.

## 교차 리뷰 (5단계 ②, 필수)
이번 작업에서 수정한 코드를 Gemini CLI로 교차 리뷰받고 반영한다. **건너뛰지 않는다.**

1. **리뷰 대상 준비 + 2. Gemini에게 리뷰 요청**: `bash .claude/skills/build-app/cross-review.sh apps/<앱> <리뷰 기준>`
   - 리뷰 기준은 4단계 구현을 시작하기 직전 커밋. 4단계를 시작할 때 `git rev-parse --short HEAD`를 HANDOFF의 `리뷰 기준:` 줄에 적어 둔다. (기준을 안 주면 커밋 전이면 `git diff`, 브랜치 작업이면 `git diff main...HEAD`)
   - 스크립트가 변경분 + 변경된 파일 전체 + 그 파일을 import·호출하는 주요 파일을 `docs/review_input.txt`(커밋 안 함)로 묶고, 정해진 질문(버그·보안·예외 처리 누락·성능만, 심각도·파일명·줄 번호·이유·수정 제안, 불확실하면 '추정')으로 `gemini -p`에 보내 `docs/review_result.md`에 저장한다.
   - Gemini가 없거나 로그인이 안 돼 있으면 스크립트가 실패한다 → 사장에게 설치·로그인을 부탁한다(`!` 한 줄씩: `winget install --id OpenJS.NodeJS.LTS -e` → `npm install -g @google/gemini-cli` → API 키: https://aistudio.google.com/apikey 에서 무료 키를 만들어 사장이 PowerShell에서 `[Environment]::SetEnvironmentVariable("GEMINI_API_KEY", "<키>", "User")` 실행. 키는 대화창에 붙여 넣지 말라고 안내. Google 계정 로그인 방식은 개인 무료 사용이 막혀 안 됨. 무료 키는 pro 모델을 못 써서 스크립트는 flash 모델을 기본으로 쓴다(`GEMINI_MODEL`로 바꿀 수 있음)). 될 때까지 5단계는 끝나지 않는다. HANDOFF에 "현재 단계: 5 (교차 리뷰 대기)"로 적는다.
   - 앱 코드가 Google 서비스로 보내진다. 안전장치가 막으면 사용자에게 `! bash .claude/skills/build-app/cross-review.sh apps/<앱> <리뷰 기준>` 실행을 부탁한다.
3. **리뷰 결과 검토**: `review_result.md`를 읽고 각 지적이 실제로 맞는지 코드를 직접 확인해 판단한다.
   - 맞는 지적은 고친다(Claude 리뷰와 같이 회귀 테스트 먼저). 틀렸거나 불필요한 지적은 반영하지 않은 이유를 `review_result.md` 맨 아래 `## Claude 판단` 절에 지적마다 적는다.
   - **심각도 '높음'인데 판단이 애매한 것은 고치지 말고 사장에게 먼저 묻는다.** (팀 안의 일은 묻지 않는다는 규칙의 예외)
   - Claude 리뷰와 같은 걸 지적하면 우선순위를 높인다.
4. **마무리**: 고친 뒤 테스트를 다시 돌려 깨진 게 없는지 확인한다. **리뷰는 1라운드만.** 고친 코드를 다시 Gemini에 돌리지 않는다. 6단계 QA 보고에 "반영한 지적 / 반영 안 한 지적(이유) / 사장 확인 필요한 것" 세 가지로 짧게 정리한다.

## 레드팀 공격 (6단계, QA 보고 전, 필수)
코드를 읽는 리뷰(5단계)와 달리, **실행 중인 앱을 해커처럼 직접 공격**한다. "구멍이 최소 1개는 있다"고 보고 찾는다.

1. 구현하지 않은 새 QA팀 에이전트에게 앱 실행 방법과 CLAUDE.md "보안 규칙"만 주고, 로컬에서 앱을 띄워 아래를 시도하게 한다.
   - **비밀값 찾기**: 빌드된 프론트 파일(웹 번들, 앱 패키지)과 커밋 기록에서 키·토큰·비밀번호 검색
   - **요청 조작**: 금액·수량·권한 값을 바꿔 API에 직접 보내기(예: 53,000원 → 0원, 일반 사용자 → 관리자)
   - **남의 데이터**: 다른 사용자의 ID로 조회·수정·삭제 요청
   - **잘못된 입력**: 빈 값, 아주 긴 값, 스크립트·SQL 조각을 넣어 서버가 막는지
   - **저장 확인**: DB에 비밀번호·민감정보가 평문으로 남는지
   - **인프라**: DB·저장소에 외부에서 바로 붙는지, 공개 범위가 기획서대로인지
2. 결과는 `docs/redteam.md`에 "시도 / 결과(막힘·뚫림) / 고친 것"으로 적는다.
3. 뚫린 것은 고치기 전에 그 공격을 재현하는 회귀 테스트를 `tests/test_review_fixes.py`(또는 같은 위치의 회귀 테스트 파일)에 먼저 넣어 실패를 확인하고, 고친 뒤 전체 테스트를 다시 돌린다.
4. 서버가 없는 앱은 "비밀값 찾기"와 "잘못된 입력"만 한다.
5. 인프라 설정을 바꿔야 하면 혼자 바꾸지 말고 사장에게 쉬운 말로 확인받는다.

## 올리기 (친구에게 링크로 보여 줘야 할 때)
- 작업 저장소에는 문서·테스트·기록이 섞여 있으므로 그대로 내보내지 않는다. 앱 파일만 담은 **공개 저장소 + GitHub Pages**를 쓴다(내역은 각자 기기에만 저장되는 앱일 때).
- 공개는 바깥에 내보내는 일이라 Claude가 직접 못 한다(안전장치가 막음). 사용자에게 **짧은 한 줄**로 실행을 부탁한다. 긴 명령은 붙여 넣다 줄이 깨지므로 스크립트 파일로 준다.
  - 처음 만들 때: 임시 스크립트로 `gh repo create <앱> --public --source <폴더> --push` + Pages 켜기(`gh api -X POST repos/<계정>/<앱>/pages -f "source[branch]=main" -f "source[path]=/"`) → 다 쓰면 지운다.
  - 다시 올리기: `apps/<앱>/deploy.sh`(상대 경로만, 임시 폴더에 공개 저장소를 받아 앱 파일만 덮어쓰고 푸시, 커밋 이름·이메일은 이 저장소 설정에서 가져옴). 사용자에게 `! bash apps/<앱>/deploy.sh`를 부탁한다.
- 올린 뒤 **공개 주소를 직접 열어** 새 버전이 반영됐는지, 핵심 기능이 되는지 확인하고 나서 링크를 준다. 주소와 다시 올리는 방법을 `apps/<앱>/HANDOFF.md`에 적는다.
- `!` 명령은 맨 앞에 띄어쓰기가 있으면 실행되지 않고 메시지로만 간다. 처음 부탁할 때 알려 준다.


## 저장소 공개 여부 (6단계 사장 OK 뒤)
- 새 프로젝트 저장소는 공개로 만들어져 있다. 앱을 다 만들고 사장 OK를 받으면 "이 저장소를 공개로 둘까요, 비공개로 바꿀까요?"를 보기 + 추천과 함께 묻는다(포트폴리오로 보여 줄 앱이면 공개 추천).
- 묻기 전에 코드와 커밋 기록에 비밀값(API 키, 토큰, 비밀번호, 개인정보)이 없는지 확인하고 결과를 함께 알린다.
- 비공개로 바꾸기: 그 폴더에서 `gh repo edit --visibility private --accept-visibility-change-consequences`. 안전장치가 막으면 사용자에게 `!` 한 줄로 부탁한다.
- 고른 결과를 `HANDOFF.md`에 적는다.
