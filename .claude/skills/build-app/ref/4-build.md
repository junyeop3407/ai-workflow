# 4단계 계획·구현 (ip·ok-ip·ui·dd·bb·cb·bf·cf) — 이 노드에 들어갈 때 읽는다

**순서**: 계획 모드(작은 앱도 3~6줄) → ok-ip 승인 때 **탐색·사용성 예상 비용**도 함께 묻고 `graph.sh budget`(계산법은 `ref/6-release.md` "탐색·사용성 점검" 1번) → (화면이 있으면) 디자인팀 `docs/DESIGN.md` + 시안 캡처(참고 서비스가 있으면 `ref/2-design.md` "참고 디자인 분석") → ★ → (서버가 있으면) 백엔드팀 저장할 데이터·기능 목록(쉬운 말로) → ★ → 구현 루프 → plan.md 단계마다 Codex 빠른 검수(cb·cf).

## 계획 모드 (4단계)
구현 계획은 **계획 모드에서 세우고 사장 승인을 받은 뒤** 구현한다. 계획 모드에서는 파일을 고치지 않고 읽기와 질문만 한다.
1. EnterPlanMode로 계획 모드에 들어간다(이미 계획 모드면 그대로). 사장에게는 승인 창이 뜨니 "계획 모드로 들어갑니다, 승인해 주세요"라고 한 줄 알린다.
   - **EnterPlanMode가 안 되거나 사장이 거절하면 그냥 진행하지 않는다.** 멈추고 "계획 모드로 바꿔 주세요(인텔리제이·터미널: `Shift + Tab`, 데스크톱 앱: 입력창 아래 모드 선택에서 Plan)"라고 부탁한 뒤, 계획 모드로 바뀐 것을 확인하고 2번으로 간다.
2. `spec.md`, `design.md`, `tests.md`를 읽는다.
3. 계획을 세우다 애매한 것(앱 이름, 패키지 ID, 화면 순서, 데이터 처리 방식 등)은 **추측하지 말고 AskUserQuestion으로 보기 + 추천을 붙여 묻는다.** 질문은 중요한 것부터, 한 번에 1~3개.
4. 계획을 작은 단계로 나누고, 단계마다 "끝났는지 확인하는 방법"(어떤 테스트가 통과하면 끝인지)을 적는다.
5. ExitPlanMode로 계획을 보여 주고 승인을 받는다. 수정 지시를 받으면 고쳐서 다시 승인받는다.
6. 승인 뒤 계획을 `docs/plan.md`에 저장하고, 질문의 답을 `spec.md` "정한 것"에 반영한 다음 디자인팀·백엔드팀 검토와 구현으로 넘어간다.

## 구현 루프 (자동, bb → bf)
"구현 → 테스트 → 실패한 것만 고치기"를 Claude가 혼자 반복하게 하는 장치.

**누가 짜나 — 개발팀** (`docs/org.md`): 코드는 **bb = `backend-dev`, bf = `frontend-dev` 에이전트**가 짠다. 메인 대화는 **개발팀 통합**(일 나누기·업무 요청서·결과 합치기·api.md 규격 조율·`progress.md`·커밋), Codex는 리뷰·통합 확인(cb·cf·cx). 메인은 bb·bf에서 앱 코드를 직접 고치지 않는다.
- **맡기기**: plan.md 단계마다 업무 요청서(`docs/org.md` "업무 요청서": 앱 폴더·이번 단계·완료 조건·참고 문서·지난 실패)를 써서 에이전트에게 준다. 같은 노드 안에서 다시 맡길 때는 새로 부르지 말고 **같은 에이전트를 이어서 부른다**(SendMessage, 기억이 이어짐).
- **맡기기 직전**(매번): `bash .claude/hooks/team-files.sh mark` — 출력된 **기준 표**(`<해시>:<해시>`)를 메인이 그대로 기억해 둔다(파일에 두지 않음).
- **받은 직후, 메인이 아무것도 쓰기 전에 확인**(매번): ① `bash .claude/hooks/team-files.sh check apps/<앱> <에이전트> <기준 표>` — Bash로 고친 것까지 저장소 전체에서 모두 그 팀 파일인지(어긋나면 그 변경을 되돌리고 다시 맡김) ② 답의 `요청:` 줄 처리 — 다른 개발 팀이면 그 에이전트에게, api.md 규격 변경이면 통합(메인)이 판단하되 사장 승인본을 바꿔야 하면 `docs/ask-later.md`, 테스트·디자인이면 담당 노드 규칙대로 ③ `progress.md`에 회차 한 줄.
- **자동 루프는 그대로**: 메인이 응답을 끝내려 하면 Stop 훅이 통과 검사를 돌린다. 실패면 실패한 테스트·원인을 업무 요청서 "지난 실패"에 넣어 같은 에이전트에게 다시 맡긴다.
- 에이전트가 "도구 없음"(스킬·context7 등)을 답하면 대신하지 않고 멈춰서 사장에게 알린다(CLAUDE.md "필요한 것이 없을 때").

다섯 칸: **목표**(노드 통과 조건) · **채점표**(bb = `백엔드 테스트:` 줄, bf = 승인된 테스트 전체 + 해시) · **일지**(`progress.md`) · **브레이크**(15회·같은 실패 3연속) · **잠금**(`.approved` + 훅).
1. 시작 전에 `cross-review.sh snapshot apps/<앱>`으로 기준점을 찍어 `progress.md` 맨 위 "단계 1 기준: <해시>"로 적는다(Codex 빠른 검수용). 4단계 시작 직전 커밋은 HANDOFF `리뷰 기준:`에.
2. **자동 루프**: 응답을 끝내려 할 때마다 Stop 훅(`graph-stop.sh` → `graph.sh loop`)이 그 노드의 통과 검사를 직접 돌린다. 실패면 막고 "실패한 테스트·한 줄 원인 → 계속 고쳐라"를 돌려주고 회차를 state.json에 센다. 통과면 자동으로 `pass` → 다음 노드(cb·cf)를 시작하라고 알린다. 사장 명령은 필요 없다. (사장이 원하면 /goal을 따로 써도 된다.)
   - **bb(백엔드)**: 앱 HANDOFF에 `백엔드 테스트: \`bash tests/backend.sh\``. 견본 `templates/backend.sh`를 복사(JUnit → 서버 켜기 → `docs/api.md` 예시 확인(`api-check.sh`) → 서버 끄기, 포트 사용 중·시간 초과·Ctrl+C 안전장치). 승인된 Playwright 테스트는 bb 통과 조건이 아니다. 백엔드 부품 테스트(JUnit)는 QA팀이 bb 시작 때 추가한다. 이때 **구조 검사 테스트**(견본 `templates/ArchitectureTest.java`를 복사해 `package`·`ROOT`만 고침)도 함께 넣어 SOLID 위반이 있으면 `./gradlew test`가 실패하게 한다(`.claude/rules/backend-solid.md` "언제 확인하나").
   - **bf(프론트)**: `테스트 실행:` 줄(승인된 테스트 전체) + 잠금 해시. api.md를 보고 붙인다.
   - 서버 없는 앱은 `graph.sh skip apps/<앱> dd,ok-dd,bb,cb "서버 없음"`(ok-ip 전에) → 합류 뒤 바로 bf.
3. **일지** `apps/<앱>/docs/progress.md` — 매 회차 한 줄 추가(커밋 전에도 파일로 남아 새 세션이 이어 받는다):
   ```
   | 회차 | 한 일 | 테스트 N/N | 실패한 테스트와 이유 | 다음 시도 |
   ```
4. **plan.md 단계 하나가 통과할 때마다**: `bash .claude/skills/build-app/cross-review.sh apps/<앱> <그 단계 기준 해시> codex` → `review_codex.md`의 맞는 지적만 고침(1라운드, 아래 "교차 리뷰" 판단 규칙) → 다음 단계 기준을 다시 `snapshot`으로 찍어 progress.md에.
5. **브레이크**: 테스트 하나를 3번 고쳐도 안 되면 superpowers:systematic-debugging으로 원인부터 찾는다. 15회 초과나 같은 실패 3회 연속이면 graph.sh가 노드를 "사장 보고"로 바꾼다 → 멈추고 사장에게 보고한다(무엇이, 왜 막혔는지, 보기 2~3개 + 추천). 사장 답을 받으면 `graph.sh resume`.
6. **다시 고칠 때**(리뷰·레드팀·점수·사장 수정 지시): `fail`로 담당 구현 노드에 돌아오면 같은 자동 루프가 다시 돈다(회차는 다시 0부터, 그 노드로 되돌아오는 횟수는 graph.md "최대" 칸).
7. **`/loop`(선택)**: 오래 걸리는 작업 중 사장이 원할 때만 — 예 `/loop 10m 테스트 돌리고 progress.md 갱신`. 세션을 닫으면 멈춘다. Claude가 혼자 켜지 않는다. 예약 작업(/schedule·데스크톱 예약)은 만들지 않는다(사장 컴퓨터는 밤에 꺼짐).

## 경영팀 (판단이 필요한 순간에만)
근거: 사장의 조직 명세 4절(경영팀), `docs/org.md`. 순서·상태·브레이크는 graph.sh·lock.sh(프로그램)가 하고, 경영팀은 **사람이 판단할 부분**만 정리한다. `manager` 에이전트는 `docs/ops.md`만 쓰고 명령을 실행하지 못한다 — 메인이 업무 요청서에 `graph.sh status`(③이면 `lock.sh status`도) 출력을 붙여 준다.
1. **요구사항 변경**(필수, graph.sh가 확인): ok-qa에서 "테스트 목록에 없는 요구·요구사항 자체가 틀림", ok-lg에서 "대체 자료·빼기"처럼 **먼저 묻기 `사장`** 실패 엣지를 쓰기 전, 그리고 이어 하는 앱에 기능을 더하기 전 → `manager`에게 영향 분석(사장 말 원문 포함) → `docs/ops.md` `## 영향 분석: <출발> → <보낼 곳>` → 분석(팀별 영향·다시 돌 노드·다시 받을 ★·추천)을 붙여 사장에게 묻기 → `graph.sh approve apps/<앱> <출발> "<사장 답>"` → `graph.sh fail …`. 분석이나 승인이 없으면 graph.sh가 거부한다.
2. **막힘 보고**(②: 되돌아온 횟수 초과·자동 루프 15회·같은 실패 3연속·점수 정체): 사장에게 보고하기 전에 `manager`에게 막힘 분석 → `## 막힘 분석: <노드>`의 사실·원인(추정)·보기·추천을 보고에 붙인다.
3. **잠금 지연**: graph.sh·테스트가 잠금을 기다리다 멈췄거나 `lock.sh status`에 "지연"이 보이면 → `manager`에게 잠금 지연 확인 → `## 잠금 지연: <잠금 이름>`. 잠금을 직접 풀거나 순서를 바꾸지 않는다(사장 승인 필요, 명세 13절).
- 경영팀 판단을 그대로 따를지는 사장이 정한다. 메인은 `ops.md`를 고치지 않는다(다시 맡김).
