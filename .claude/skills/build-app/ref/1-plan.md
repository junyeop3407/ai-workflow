# 1단계 기획 (req·ok-req·lg·ok-lg) — 이 노드에 들어갈 때 읽는다

**순서**: 기획 인터뷰(손으로 하던 일을 대신하는 앱이면 "견본 파일"도) → 견본 `templates/requirements.md`로 기획서(성공 기준·빈칸 점검표·기능마다 수용 기준·하지 않을 것·화면 흐름도 Mermaid) → **Gemini 기획서 비판** `bash .claude/skills/build-app/doc-review.sh apps/<앱>`(1라운드, 맞는 지적 반영 + `## Claude 판단`) → ★기획 검토 → 법무 검토 → OK 뒤 명세서(사장 검토 대상 아님, 쓰다 "아직 안 정한 것"이 나오면 AskUserQuestion).

## 기획 인터뷰 (1단계, 빈칸 점검표)
근거: Anthropic 모범 사례("스펙을 쓸 수 있을 때까지 인터뷰"), grill-me(결정 트리를 가지별로), Spec Kit clarify(한 바퀴 최대 5문항). 분석: `docs/front-stage-review.md`.
1. **첫 질문은 성공 기준**: "이 앱을 쓰면 무엇이 얼마나 나아지나요?"(보기: 시간 줄이기 / 실수 줄이기 / 돈 / 재미, 추천 포함) → 측정하거나 눈으로 확인할 수 있는 한 줄로 바꿔 다시 확인받는다.
2. **빈칸 점검표**(`templates/requirements.md` "## 빈칸 점검표")의 칸마다 `정함: <답>` / `나중: <이유>` / `해당 없음`이 될 때까지 묻는다. 남은 칸은 `묻기`로 적어 두면 graph.sh가 req를 통과시키지 않는다.
3. 묻는 순서: **앞선 결정부터**(누가·왜 → 무엇 → 어떻게). 앞 답에 따라 뒤 질문이 바뀐다(결정 트리).
4. 한 번에 1개, 보기 2~4개 + **추천과 이유**(초보 사장 기준). 한 바퀴 최대 5문항 → 기획서 초안을 보여 주고 다음 바퀴.
5. **저장소·견본 파일·이전 앱 문서로 알 수 있는 것은 묻지 않고 직접 찾는다.** 지어내지도 않는다.
6. **되돌리기 어려운 동작**(돈 결제·메시지 발송·삭제)이 있으면 "사용자에게 한 번 더 묻기 / 되돌리기 / 기록" 중 무엇을 할지 묻고, 그 확인 절차를 기능의 수용 기준으로 넣는다.
7. **기능 분류**(Kano): 기능마다 "꼭 있어야(없으면 화남) / 많을수록 좋음 / 있으면 놀람" 중 하나를 클릭으로 고르게 한다(추천 포함).
8. **첫 버전 자르기**(User Story Mapping의 걸어 다니는 뼈대): 1차 = "꼭" + 핵심 "많을수록"으로, **1차 기능만으로 사용자가 처음부터 끝까지 한 번 쓸 수 있어야** 한다(화면 흐름도가 1차 기능만으로 이어지는지 확인). "놀람"은 기본 `나중`(사장이 원하면 1차). 기능 줄: `- F1 [1차·꼭] <기능>`. `나중` 기능은 테스트·구현·점수에서 빠진다.
9. 1차 기능마다 **수용 기준** 1~3줄 + **구체 예시**(Example Mapping): `F1-1 <언제/조건>이면 앱은 <보이는 결과>를 한다 — 예: <입력 값 → 결과 값>`(EARS 꼴). 예외(빈 값·실패·끊김·권한 없음) 하나 이상. 테스트는 예시 값을 그대로 쓴다. 예시를 못 정하면 그 칸은 `묻기`.
10. **출시 안내문 + 예상 질문**(Working Backwards): 다 만들었다고 치고 사용자에게 보내는 안내 3문장과 예상 질문 3개를 기획서 맨 위에. 무엇이 좋아지는지 안 보이면 기능을 다시 본다. 마지막 QA 보고 때 "안내문에 없는 걸 만들었나(과잉)"를 같이 본다.
11. **화면 초안**(화면이 있는 앱): 1차 화면마다 회색 상자만으로 "어디에 뭐가 있고 어디로 넘어가나"를 그린 HTML 한 장(`docs/wireframe/<화면>.html`, 색·글꼴·꾸밈 없음 — 디자인은 4단계 디자인팀)을 만들고 캡처(`docs/wireframe/<화면>.png`, Playwright `npx playwright screenshot` 또는 내장 브라우저)해 ★기획 검토 "볼 것"에 넣는다. 사장이 흐름이 틀렸다고 하면 기능·흐름도를 고친다. 점검표 `화면 초안` 칸은 화면이 없으면 `해당 없음`.
12. 끝나는 조건: 점검표에 `묻기` 0개 + Gemini 비판의 [맞음] 반영 → ★기획 검토.

## 견본 파일 (변환 전/후, 1·3단계)
엑셀 양식 바꾸기, 제안서·보고서 만들기처럼 **사람이 손으로 하던 일을 대신하는 앱**은 말로 설명받는 것보다 실제 파일이 정확하다. "이걸 넣으면 → 이게 나와야 한다"는 파일 한 쌍이 곧 요구사항이자 테스트 정답이다.
1. **1단계에서 묻는다**: "지금 쓰는 변환 전 파일과, 손으로 완성한 변환 후 파일을 2~3쌍 주실 수 있나요?" (보기: 있다 / 나중에 / 없다, 추천: 있다). 이름·연락처·주소·원가처럼 민감한 칸이 있는지도 함께 묻는다.
2. **실제 파일은 `apps/<앱>/samples/`에 둔다.** 이 폴더는 `.gitignore`로 빠져 있어 커밋되지 않는다(다른 컴퓨터로 따라가지 않으니 HANDOFF에 "견본은 사장 컴퓨터에만 있음"이라고 적는다).
3. **테스트용 가짜 견본을 만든다**: 실제 파일과 칸·순서·형식은 똑같이, 내용은 가짜(홍길동, 010-0000-0000, 원가 1000원 등)로 바꿔 `apps/<앱>/tests/fixtures/`에 둔다. 변환 후 파일도 같은 가짜 값으로 만든다. 실제 파일을 그대로 복사하지 않는다.
4. 실제 파일을 보며 찾은 규칙(어느 칸이 어디로 가는지, 합치기·나누기, 날짜·숫자 형식, 빈 칸 처리)은 `spec.md`에 한 줄씩 적는다. 파일만 보고 알 수 없는 규칙은 지어내지 말고 묻는다.
5. **3단계 테스트**: 가짜 견본 입력 → 앱 결과가 가짜 정답 파일과 칸 하나하나 같은지 비교하는 테스트를 맨 앞에 둔다. 사장이 실제 파일로도 확인하고 싶으면 6단계에서 `samples/`로 직접 돌려 보여 준다(결과 파일도 커밋하지 않는다).
- 데이터 파일(`.xlsx`·`.xls`·`.csv` 등)은 `tests/fixtures/` 밖에서는 커밋하면 훅(`guard-git`)이 막는다. 막히면 가짜 견본으로 바꿔 `tests/fixtures/`로 옮긴다.

## 명세서 (`docs/spec.md`, Claude 파악용)
사장에게 보여 주는 기획서(`requirements.md`)와 달리, **Claude가 스스로 앱을 정확히 파악하려고 쓰는 작업 기준 문서**다. 대화가 길어지거나 새 세션·다른 컴퓨터에서 이어 할 때 이 파일만 읽으면 앱 전체를 알 수 있어야 한다.
- 들어갈 것:
  - 앱 한 줄 설명, 누가 쓰는지
  - 기능마다: 화면, 동작, 예외 상황(빈 화면, 잘못된 입력, 연결 끊김 등)
  - 데이터 구조: 항목, 필수값, 관계, 삭제·보관 규칙
  - 정한 것: 사장이 질문에 답해 정한 것을 한 줄씩(무엇을, 왜)
  - 아직 안 정한 것: **지어내지 말고 여기에 적는다.** 구현에 필요해지면 AskUserQuestion으로 묻는다
- 갱신: 2단계에서 고른 설계, 4단계 계획 모드의 답, 6단계 수정 지시로 바뀐 내용은 그때그때 반영한다. 코드와 spec이 다르면 사장이 마지막에 정한 쪽에 맞추고 다른 쪽을 고친다.

## 법무 검토 (lg·ok-lg, 그리고 sa의 출시 전 점검)
근거: 사장의 조직 명세 10절(법무팀), `docs/org.md`. **법률 자문이 아니다** — 위험이 크면 변호사 확인을 권한다.
1. **건너뛰기**: 기획서 `## 외부 자료·데이터`와 `## 개인정보`가 **둘 다** `- 없음`이면 ok-req 통과 직후 `graph.sh skip apps/<앱> lg "법무 해당 없음"`(ok-lg도 함께 건너뜀). 로그인이 있으면 개인정보가 있는 것이다.
2. **맡기기**: `legal` 에이전트에게 업무 요청서(앱 폴더, 단계 `lg`, 참고 문서 requirements.md). 에이전트는 `docs/legal.md`만 쓸 수 있고(훅) 명령을 실행하지 못한다. 외부 자료가 6개 이상이면 출처별로 `legal`을 동시에 여러 번 불러 **조사만**(쓰지 말라고) 시키고, 마지막 한 번에 결과를 넘겨 `legal.md`를 쓰게 한다(조사는 병렬, 최종 판정은 한 번에 하나).
3. `graph.sh pass apps/<앱> lg` — 형식 검사(graph.md "법무 판정서 검사"). 판정 내용은 메인이 고치지 않는다(법무 결과 무효화 금지). 틀린 것 같으면 근거를 붙여 `legal`에게 다시 맡긴다.
4. **★법무 검토**(ok-lg): GREEN은 조건만 한 줄로, **YELLOW·RED는 항목마다** "조건부로 진행 / 대체 자료 찾기 / 기능에서 빼기"(추천 포함)를 묻는다. 고른 답을 approve 내용에 적는다. 대체·빼기면 `graph.sh fail apps/<앱> ok-lg "<답>" req`(기획서 고친 뒤 다시 lg).
5. **출시 전(sa)**: security-audit과 함께 `legal`에게 단계 `sa`로 맡겨 `legal.md` `## 출시 전 점검`(라이선스 고지·약관이 실제 동작과 맞는지)을 채운다. 체크리스트 21·22번의 근거가 된다. 고지가 없으면 bf로 고친다.
