# AI 가상오피스 적용 안내서 — ai-workflow에서 한 것 전부(Docker 제외)

> **이 문서 쓰는 법**
> - 가상오피스 프로젝트의 Claude Code에게 이 파일을 통째로 주고 "이 안내서대로 적용해. 먼저 현재 구조를 분석하고, 항목마다 계획을 보여 준 뒤 하나씩 해"라고 하면 된다(맨 끝 "Claude Code에게 줄 지시문").
> - ai-workflow는 **파일 + bash 스크립트 + Claude Code 훅**으로 도는 작업장이고, 가상오피스는 **화면·서버·DB가 있는 앱**이다. 그래서 같은 원칙을 이렇게 바꿔 읽는다:
>
> | ai-workflow에서 | 가상오피스에서 |
> |---|---|
> | 훅(명령 실행 직전 검사) | 서버의 권한 검사 미들웨어·API 검증 |
> | 파일 경계(이 팀은 이 파일만) | 자원 경계(이 에이전트는 이 테이블·이 문서·이 API만) |
> | `state.json`(진행 상태) | DB의 작업·상태 테이블 |
> | `mkdir`로 잠금 | DB 유일 제약·조건부 갱신·트랜잭션(`SELECT … FOR UPDATE` 등) |
> | `docs/legal.md`·`docs/ops.md` | 법무 판정·경영 분석 레코드(소유 에이전트만 쓰기) |
> | git `pre-push` 훅 | 서버가 "실제로 일어나는 일"을 보고 막는 최종 검사 |
>
> - 근거 명세: 사장의 「AI 가상오피스 조직 구조 및 에이전트 운영 명세서」, 「병렬·직렬 처리 및 동시성 제어 통합 명세서」. ai-workflow 쪽 실제 구현 파일은 항목마다 적었다(참고용으로 읽어 보면 된다).

## 0. 먼저 — 전체를 관통하는 원칙 7개 (가장 중요)

이번 작업에서 자동 보안 리뷰가 **20번 넘게** 우회 방법을 찾아냈고, 고치면서 얻은 원칙이다. 가상오피스의 모든 검사·권한·잠금은 이 원칙으로 만든다.

1. **기본은 거부(목록에 있는 것만 허용).**
   - 왜: "이건 막는다" 목록(블랙리스트)은 항상 빠진 게 생긴다. 실제로 "목록에 없는 파일은 프론트 몫"으로 했다가 `package.json`·테스트 설정을 고쳐 테스트를 약하게 만드는 길이 열렸다.
   - 하면 안 됨: 새 자원·새 API가 생겼을 때 자동으로 허용되는 구조.
2. **검사는 "실제로 일어나는 일"을 보는 곳에서.**
   - 왜: 명령 글자를 읽어 막는 검사는 따옴표·별명·옵션 끼우기로 계속 뚫렸다(`git -c … commit`, `"--no-verify"`, `d"o"cker`). 결국 git 자체 훅(`pre-push`)과 GitHub 브랜치 보호처럼 **실제 행동 시점**에 막는 장치를 마지막 방어선으로 뒀다.
   - 가상오피스: 화면·에이전트가 보낸 "요청 글자"가 아니라 **서버가 실제로 바꾸려는 데이터**를 보고 권한을 판단한다. 클라이언트(화면) 검사는 편의일 뿐 방어가 아니다.
3. **검사 전에 정규화(같은 뜻이면 같은 글자로).**
   - 왜: 대소문자(`Src/Main/Java`), `//`·`./`·`../`, Windows가 바꿔 읽는 이름(`App.tsx.`, `PROGRA~1`, `a:stream`), 따옴표·역슬래시 섞기가 전부 우회 길이었다.
   - 가상오피스: ID·경로·이름은 정규화한 뒤 비교하고, 이상한 글자가 섞이면 **판단하지 말고 거부**.
4. **모르면 막기(fail closed).**
   - 왜: 파싱 못 하는 입력, 확인 못 한 상태를 통과시키면 그게 뒷문이 된다(예: 테스트 개수를 못 읽으면 통과로 치지 않음, 테스트 줄이 없는 앱 코드는 main에 못 올림).
5. **진짜 파서를 쓴다(정규식으로 구조를 자르지 않는다).**
   - 왜: JSON 안에 `","x":`를 끼워 넣어 뒤 명령을 숨기는 속임수가 실제로 통했다. YAML도 줄 단위로 읽다가 긴 문법·앵커로 뚫렸다.
   - 가상오피스: 요청 본문은 JSON 파서·스키마 검증으로. 정규식 자르기 금지.
6. **"글자 막기"는 과속 방지턱, 문서에 그렇게 적는다.**
   - 왜: 사람(사장)이 "막혀 있다"고 믿으면 위험하다. 어떤 검사가 진짜 방어고 어떤 게 편의인지 문서에 구분해 둔다.
7. **감시 장치를 느슨하게 하는 변경은 AI가 혼자 하지 않는다.**
   - 왜: ai-workflow에서 "원격 임시 브랜치 삭제 허용"을 넣으려 하자 Claude Code 안전 검사가 막았다. 보안 장치 완화는 사장이 직접(사장 계정·`!` 명령)으로만.
   - 가상오피스: 권한 완화·잠금 강제 해제·순서 변경 같은 기능은 **프로젝트 총괄(사용자) 권한으로만** 실행되게.

## 1. 조직 구조 — 팀·역할 결정

ai-workflow 구현: `CLAUDE.md` "팀별 기본 기술" 표, `docs/org.md`(조직도·책임표·업무 요청서), `.claude/agents/*.md`.

### 1-1. 최종 조직 (ai-workflow는 비서 제외, 가상오피스는 명세대로 비서 포함)
| 조직 | 구성 | 핵심 책임 |
|---|---|---|
| 사장(프로젝트 총괄) | 사용자 | 방향·범위·★ 승인·공개 결정 |
| 기획팀 | 기획 에이전트 | 무엇을 만들지: 기획서·기능·수용 기준 |
| 디자인팀 | 디자인 에이전트 | DESIGN 규칙·시안 |
| 개발팀 | **통합(오케스트레이터)** + Codex(리뷰·통합 확인) + 백엔드·프론트엔드 서브에이전트 | 구현 |
| QA팀 | QA Reviewer + Test Runner | 테스트 기준·평가 / 실행 |
| 보안 검증팀 | Red Team | 공격자 관점 점검(고치지 않음) |
| 법무팀 | Legal | 외부 자료·개인정보·라이선스 GREEN/YELLOW/RED |
| 경영팀 | Manager | 판단이 필요한 순간의 영향 분석·막힘·잠금 지연 |
| 공통 지원 | Gemini | 조사·기획서 비판·교차 리뷰. 결정권 없음 |
| (가상오피스) 비서 | Secretary | 요청 접수·보고·기록 — 순서·잠금은 못 바꿈 |

### 1-2. Codex = "개발팀 리뷰·통합 확인 담당" (구현하지 않음) — 사장 결정
- **무엇**: 명세는 Codex를 "개발팀 총괄"로 두지만, Codex는 코드를 짜지 않고 단계마다 빠른 검수·전체 교차 리뷰·통합 확인만 한다.
- **왜**: **만든 AI와 다른 AI가 검사**해야 리뷰가 독립적이다. Codex가 구현까지 하면 Codex 리뷰가 "자기 코드 검사"가 되어 의미가 없어지고, 사용량도 두 배로 든다.
- **하면 안 됨**: Codex에게 구현과 리뷰를 같이 맡기기. 리뷰어가 쓰기 권한을 갖기(ai-workflow에서 Codex는 빈 임시 폴더에서 읽기 전용으로 돈다).

### 1-3. 백엔드·프론트엔드 = "진짜 팀 에이전트" — 사장 결정
- **무엇**: 메인이 모자만 바꿔 쓰는 방식이 아니라, 별도 에이전트(`backend-dev`, `frontend-dev`)가 실제로 코드를 짠다. 메인(오케스트레이터)은 **통합만**: 일 나누기·업무 요청서·결과 합치기·API 규격 조율·기록·커밋.
- **왜**:
  - 각 에이전트가 받은 요청서·명세만 보므로 명세서 취지(전문 영역 분리)와 맞는다.
  - 팀마다 지시문을 따로 줄 수 있다(백엔드는 SOLID·보안 규칙, 프론트는 디자인 규칙).
  - 실무는 sonnet, 판단은 opus — 사용량 절약.
- **자동 루프는 오케스트레이터에 그대로 둔다**: "테스트 실패 → 실패 내용을 붙여 같은 에이전트에게 다시 맡김"을 오케스트레이터가 돌린다. 같은 노드 안에서 다시 맡길 때는 **새로 부르지 말고 이어서**(기억 유지).
- **기본은 백엔드 → 프론트 순서**: 프론트 테스트가 돌려면 서버가 떠 있어야 해서. 명세의 "병렬 개발"은 API 규격이 확정된 뒤의 선택 사항으로 남겼다(그래프 변경·사용량 증가).
- **하면 안 됨**: 오케스트레이터가 구현 단계에서 앱 코드를 직접 고치기(경계가 무너짐). 에이전트가 커밋·배포하기(통합 담당만).

### 1-4. 업무 요청서와 답 형식 (명세 17절)
- **요청서 필수 5줄**: 대상(앱·작업 공간) / 이번 일(계획 단계 번호) / 완료 조건(통과해야 할 테스트·수용 기준) / 참고 문서 / 기준점(시작 시점 스냅샷). 해당되면: 지난 실패, 다른 팀이 넘긴 요청, 하지 말 것.
- **답 형식 5줄**: 결과(테스트 N/M, 시도 K번) · 바꾼 것 · 한 일 · **요청(다른 팀에 넘길 것)** · 막힌 것.
- **왜**: 인수인계 누락·추측 방지. "요청:" 칸 덕분에 에이전트가 남의 영역을 고치지 않고 넘긴다.
- **하면 안 됨**: 에이전트가 다른 팀 자원을 "직접 고치고 보고"하기 → 반드시 `요청(팀): 무엇을 왜`로 넘긴다.

### 1-5. 책임표 + 공통 행동 규칙
- 업무마다 **최종 책임 조직 하나**, 다른 팀이 하면 안 되는 것을 표로(ai-workflow `docs/org.md` "누가 최종 책임인가").
- 공통 규칙 6개: 자기 일만(남의 결과는 요청으로) / 사실과 추측 구분("추정") / 외부 자료는 출처·확인 날짜 / 결과물·실행 결과 없이 "끝" 금지 / 요구사항·설계·일정 변경은 이유와 승인자 기록 / 일은 요청서로 넘김.
- **가상오피스 화면**: 팀 카드에 목적·소속 에이전트·담당 업무·권한·제한을 보여 주고, **역할 설명과 실제 에이전트 시스템 프롬프트·권한이 서로 같게**(명세 19.1).

### 1-6. 모든 팀 결과물은 사장 검토 (★)
- 각 팀 결과물(기획서·법무 판정·설계안·테스트 목록·계획·디자인·데이터/API·QA 보고·공개 여부)은 사장 OK 전 다음 단계로 못 간다. 수정 지시는 고친 뒤 "해결됐어요 / 아직이에요"를 물어 "해결됐어요" 전엔 "완료" 금지.
- **왜**: 사용자가 최종 결정권자(명세 3절). 사람이 확인하는 지점이 없으면 AI끼리 잘못된 방향으로 계속 간다.
- **반대로 묻지 않을 것**: 팀 내부 일(계획·코드·테스트·고치기·내부 리뷰·기록)은 묻지 않는다. 구현~QA 보고 사이 질문 0번 — 애매한 건 "나중에 물을 것"에 모아 QA 보고 때 한 번에.

## 2. 팀별 자원 경계 (이 팀은 이것만 고친다)

ai-workflow 구현: `.claude/hooks/team-files.sh`(+ `settings.json` 등록, 에이전트 파일 frontmatter 훅 두 겹), 시험 `test-hooks.sh`.

### 2-1. 무엇
| 담당 | 고칠 수 있는 것 (목록에 있는 것만) |
|---|---|
| 백엔드 | 서버 코드·서버 빌드 설정 |
| 프론트엔드 | 화면 코드·화면 설정(목록으로) |
| 법무 | 법무 판정서 하나 |
| 경영 | 운영 기록 하나 |
| **둘 다 못 고침** | 테스트(어디 있든 `*.test.*`·`*.spec.*`·`__tests__`), 테스트 실행 설정, 패키지 설정(`package.json`·잠금 파일 — 패키지 추가는 통합에 요청), 승인된 문서(기획서·DESIGN·API 규격), 진행 상태, 비밀값, 무시 목록(.gitignore) |

### 2-2. 왜
- QA 독립성(명세 8.4): 개발팀이 테스트·테스트 설정을 고치면 "테스트를 약하게 만들어 통과"가 가능해진다.
- 법무·경영 결과를 다른 팀이 바꾸지 못하게(명세 10.6, 4.5).
- 사장 승인본(기획서·API 규격)을 구현 팀이 몰래 바꾸지 못하게.

### 2-3. 가상오피스에 적용
- **서버에서** 에이전트 ID별 쓰기 권한(자원 종류·자원 ID 단위)을 검사한다. 화면에서 버튼을 숨기는 건 방어가 아니다.
- 권한 표는 **기본 거부**: 표에 없는 자원은 아무 에이전트도 못 씀.
- 에이전트가 남의 자원을 바꿔야 하면 → 쓰기 대신 "요청" 레코드 생성(담당 팀 대기열로).
- **사후 확인도 둔다**: 즉시 차단(요청 시점)만으로는 다른 경로(대량 작업·스크립트)를 놓친다. ai-workflow는 위임 직전 상태를 찍고(`mark`) 답을 받은 직후 비교(`check`)해서, 그 사이 바뀐 모든 것이 그 팀 몫인지 본다.
  - 기준점은 **조작할 수 없게**: 처음엔 저장소 안 파일에 기준을 저장했다가 "에이전트가 기준 파일을 고쳐 쓸 수 있다"는 지적을 받고, **내용 해시로 주소가 정해지는 값**을 오케스트레이터가 직접 들고 있게 바꿨다. 가상오피스: 기준 스냅샷 ID는 서버가 발급·보관하고 에이전트는 못 건드리게.

### 2-4. 보안 리뷰로 막은 우회 (가상오피스에서도 같은 종류가 생긴다)
| 우회 | 막은 방법 |
|---|---|
| 경로에 `apps/`를 한 번 더 넣어 남의 폴더처럼 보이게 | 저장소 기준 **맨 앞** `apps/<앱>/`만 벗기고 판단 |
| `//`, `./`, `../`, 대소문자, `App.tsx.`, `PROGRA~1`, `a:stream` | 정규화 + 이상한 글자 있으면 거부 |
| 저장소 밖 절대 경로 | 저장소 실제 위치 기준으로 안쪽인지 |
| 잠긴 파일을 다른 폴더로 **옮겨** 원래 자리에서 사라지게 | "이름 바꾸기" 감지를 끄고 지운 쪽·생긴 쪽 둘 다 검사 |
| `.gitignore`에 넣어 숨긴 새 파일·비밀 파일 수정 | 무시 파일도 내용 해시로 비교(개수 제한 없이) |
| git 설정·git 훅 폴더 변경(바로가기·실행 권한만 바꾸기 포함) | 설정·훅 내용 + 종류·권한·바로가기 대상까지 해시 |

### 2-5. 하면 안 되는 것
- "목록에 없으면 프론트 몫"처럼 **기본 허용**으로 두기 — 실제로 테스트 설정을 고치는 뒷문이 됐다.

- 검사 기준점을 에이전트가 쓸 수 있는 곳에 저장하기.

## 3. 법무팀

ai-workflow 구현: `.claude/agents/legal.md`, 그래프 노드 `lg`→`★ok-lg`(`graph.md`·`graph.sh legal_ok`), 기획서 견본 `## 외부 자료·데이터`·`## 개인정보`, 체크리스트 21·22, 시험 `test-graph.sh`.

### 3-1. 흐름
`기획 → ★기획 검토 → 법무 검토 → ★법무 검토 → 설계안 …` + 출시 전(보안 감사 단계)에 한 번 더.

### 3-2. 무엇을 어떻게
- **에이전트 권한**: 판정서 하나만 쓴다, **명령 실행 권한 없음**(그래야 쓰기 제한이 훅 하나로 완전히 지켜짐), 웹에서 약관·라이선스 원문 조사 가능. 모델 opus(판단, 드물게 호출).
- **기획서에 칸 두 개**: `외부 자료·데이터`(이름 — 출처 — 쓰는 방식: 내부 참고/화면 표시/AI 학습/RAG/재배포/상업 이용), `개인정보`(로그인 있으면 해당).
- **판정 형식(프로그램이 검사, 하나라도 어기면 다음 단계 못 감)**:
  1. "법률 자문이 아님" 안내 문구
  2. 판정 줄 `- [GREEN|YELLOW|RED] <대상> — 쓰는 방식 — 조건 — 근거: <원문 주소> (<확인 날짜>)`
  3. RED는 `조치:` 필수(빼기/대체/허가)
  4. 기획서의 외부 자료 **하나하나가 빠짐없이** 판정돼야
- **YELLOW·RED는 판정 단계에선 통과**시키고, 쓸지 말지는 ★법무 검토에서 사장이 "조건부 진행 / 대체 자료 / 빼기" 중 고름. 대체·빼기면 기획으로 되돌림(이때 경영팀 영향 분석 필수 — 6절).
- **건너뛰기**: 외부 자료와 개인정보가 **둘 다 없음**일 때만, 판정·★ 둘 다 함께.
- **출시 전 점검**: 오픈소스 라이선스 고지(고지 화면·NOTICE), 약관·개인정보처리방침이 실제 동작과 맞는지. 체크리스트 21(라이선스 고지)·22(RED 안 씀, YELLOW는 사장이 고른 조건대로만).
- **병렬·직렬(동시성 명세 6-6)**: 출처가 많으면 출처별 조사는 동시에(쓰기 금지), **최종 판정서 작성은 한 번에 하나**.

### 3-3. 왜
- 명세 10절: 자료 수집부터 저장·가공·AI 활용·공개까지 단계별 위험 확인, 검토 전 불확실한 자료는 쓰지 않는 것이 기본값.
- 형식 검사를 프로그램이 하는 이유: AI가 "근거 없이 GREEN"을 주거나 자료를 빠뜨리는 걸 사람이 매번 확인하기 어렵다.

### 3-4. 하면 안 되는 것
- 법무 판정을 오케스트레이터·다른 팀이 고치기 → 틀려 보이면 근거를 붙여 법무에 **다시 맡긴다**.
- AI가 법 위반 여부를 확정 보증하기 → 불확실성·관할·최신성 명시, 위험 크면 변호사 권고.
- YELLOW를 사람 확인 없이 "조건부 사용"으로 자동 진행하기.
- robots.txt만 보고 허용 판단(참고 신호일 뿐).

## 4. 병렬·직렬 처리 — 자원별 잠금

ai-workflow 구현: `.claude/hooks/lock.sh`(acquire·release·check·run·status), `graph.sh`(`state:<앱>`), `check-tests.sh`·`backend.sh`(`env:port:<번호>`), 시험 `test-lock.sh` 22개 + `test-graph.sh` 6개.

### 4-1. 무엇
- **전역 잠금 하나가 아니라 자원 이름마다**: `state:<앱>`(진행 상태 읽고 고치기), `env:port:<번호>`(테스트·서버 포트). 서로 다른 앱·포트는 기다리지 않고 동시에.
- **원자적 획득**: 동시에 해도 한 명만 성공하는 연산으로(ai-workflow는 폴더 만들기). 가상오피스는 **DB 유일 제약/조건부 갱신/트랜잭션**으로.
- **FIFO 번호표**: 번호표도 원자적으로 발급. 살아 있는 번호표 중 가장 작은 번호만 잡을 수 있음.
- **번호표에 고유 꼬리표(순번-프로세스-난수)** ← **실제로 만난 버그**: 죽은 대기자의 번호표가 치워진 뒤 다음 사람이 **같은 번호**를 받자, 아직 돌던 죽은 대기자 프로세스가 "내 차례"로 착각해 남의 번호표를 지우고 잠금을 가져가 진짜 대기자가 영영 못 잡았다. → 번호표 이름을 고유하게 + **내 번호표가 사라졌으면 그 자리에서 그만둠**.
- **죽은 소유자만 회수**: 잡은 프로세스가 **실제로 끝났을 때만** 회수. 시간이 지났다고 회수하지 않고 "지연"으로 표시만 → 경영팀·사장 보고(명세 11-3·11-4).
- **세대 번호(fencing token)**: 잡을 때마다 1씩 오른다. 상태를 쓰기 **직전에** "내 세대가 아직 최신인가" 확인 → 회수된 옛 작업이 늦게 깨어나 덮어쓰지 못함.
- **다시 들어가기**: 이미 잡은 작업이 부른 하위 작업은 같은 잠금을 기다리지 않음(교착 방지). 여러 자원은 **정렬된 순서로** 잡음(교착 방지).
- **실패·중단해도 풀림**, 기다리다 중단되면 자기 번호표를 지움.
- **기록**: 잡음·풂·회수·시간 초과·번호표 사라짐.
- **읽기 명령은 잠그지 않음**: 상태 보기는 언제나 됨(다른 검사가 안에서 불러도 막히지 않게).
- **포트**: 앱마다 다른 포트를 정해 적는다. 안 적으면 모든 앱이 `default` 하나에 줄 섬 — **위험을 판단 못 하면 안전하게 직렬**(명세 16-2 마지막 문단).

### 4-2. 왜
- 실제로 부딪히는 곳: 세션 두 개가 같은 앱 상태를 동시에 고쳐 기록이 사라짐 / 테스트 두 개가 같은 포트를 써서 서로 깨짐(→ 자동 루프가 테스트 실패로 오해).
- 명세 원칙: 독립 작업은 병렬, 같은 자원은 FIFO 직렬, 실패해도 대기열이 멈추지 않음, 오래된 작업의 늦은 반영 차단.

### 4-3. 가상오피스에 적용
- 명세 16절이 이미 요구하는 것과 같다: Queue Manager·Lock Manager·상태·Recovery. **메모리 변수·클라이언트 상태로 구현 금지**, 서버 측 영속 저장소에.
- 위 "번호표 재사용" 버그와 같은 종류가 DB에서도 생긴다: 대기 행의 ID를 재사용하지 말 것(시퀀스·UUID), 대기자는 매번 "내 행이 아직 있는지" 확인.
- 회수 판단은 "lease 만료"만으로 하지 말고 **실행 주체가 살아 있는지(heartbeat)**까지. 만료 + 하트비트 끊김일 때만 회수, 회수 뒤에는 세대 번호로 옛 작업의 쓰기를 거부.
- 화면: 팀 상세에 처리 중·대기 수·잠금 소유·점유 시간·지연 표시(명세 15절). **대기 중인 에이전트를 "작업 중"으로 표시하지 않기**.

### 4-4. 하면 안 되는 것 / 일부러 안 한 것
- 전역 잠금 하나로 전부 직렬화 — 독립 작업까지 기다리게 됨.
- 시간만 보고 강제 회수 — 아직 도는 작업과 겹쳐 데이터가 깨짐.
- 잠금 강제 해제·순서 변경을 비서·경영팀이 직접 — 사장 승인 필요(명세 13·14절).
- **git 커밋·푸시는 따로 잠그지 않았다**: git이 자기 잠금(`index.lock`)이 있고 부딪혀도 망가지지 않고 실패만 하므로(다시 하면 됨). "이미 안전하게 실패하는 곳"엔 잠금을 더하지 않는다.
- **중복 요청(멱등성)은 별도 장치 없이**: 메인 한 명이 맡기므로 요청서의 "이번 일(단계 번호)"로 구분. 가상오피스처럼 여러 주체가 요청을 보내는 앱이면 **멱등성 키를 꼭 둔다**(명세 12절).

### 4-5. 시험 시나리오 (명세 17절에서 맞는 것 — 그대로 옮겨 쓸 것)
잡기·풀기·남의 토큰 거부 / 동시 6개 → 덮어쓰기 0·겹침 0 / 대기 1·2·3이 접수 순서대로 / 독립 자원은 바로 실행 / 실패해도 풀림 / 죽은 소유자 회수 + 옛 토큰 거부 / 살아 있는데 오래 걸림 → 회수 안 하고 지연 표시 / 시간 초과 대기자 번호표 삭제 / 앞 대기자를 부른 쪽이 죽어도 뒤가 잡음 / 종료 신호 받은 대기자 번호표 삭제 / 다시 들어가기 교착 없음 / 반대 순서 다중 잠금 교착 없음 / 기록 남음 / 쓰는 명령 둘 동시 → 기록 둘 다 남음.
- **시험 작성 주의(실제로 겪음)**: 백그라운드로 띄운 "가짜 소유자"를 `$(…)` 안에서 띄우면 그 프로세스가 끝날 때까지 기다린다. 끈 프로세스는 즉시 거둬들여야(좀비면 살아 있는 걸로 보임).

## 5. 경영팀

ai-workflow 구현: `.claude/agents/manager.md`, `graph.sh ops_ok`(먼저 묻기 엣지 검사), `graph.md` 실패 엣지 표 "먼저 묻기", 시험 `test-graph.sh`.

### 5-1. 무엇
- **판단이 필요한 순간에만** 부른다:
  1. **요구사항 변경**(필수, 프로그램이 강제): QA 보고에서 "테스트 목록에 없는 요구·요구사항 자체가 틀림", 법무 검토에서 "대체·빼기", 이어 하는 앱에 기능 추가 → 영향 분석: 팀별로 다시 손봐야 할 결과물(기획서·법무·테스트·API·디자인·코드 — **영향 없는 것도 "없음"으로**), 다시 돌 단계, 다시 받을 ★ 승인, 예상 비용("추정"), 추천(지금/나중/줄여서).
     - 프로그램 규칙: 요구사항을 바꾸는 되돌리기는 **영향 분석 기록(영향·다시 돌 단계·추천 줄이 다 있어야) + 사장 승인 기록**이 둘 다 있어야만 실행. 단순 수정 지시("아직이에요")는 요구사항 변경이 아니라 바로.
  2. **막힘 보고**(같은 실패 반복·횟수 초과·점수 정체) 전에 원인 분석·보기·추천.
  3. **잠금 지연·대기 시간 초과** 때 원인 확인(죽은 세션인지, 같은 포트를 두 앱이 쓰는지).
- **권한**: 운영 기록 하나만 쓰기, 명령 실행 없음(상태는 오케스트레이터가 요청서에 붙여 줌), **제안만** — 사장이 정하고 프로그램이 실행.

### 5-2. 왜 이렇게
- 순서·상태·브레이크·병목 감지는 이미 **프로그램**(그래프·잠금)이 한다. AI가 같은 일을 다시 하면 **중복이고 틀릴 수 있다**. 그래서 경영팀은 "사람이 판단할 부분"만.
- 요구사항 변경은 여러 팀 결과물을 무효로 만드는 가장 비싼 사건 — 영향을 모른 채 되돌리면 승인된 테스트·법무 판정이 조용히 어긋난다.

### 5-3. 하면 안 되는 것
- 경영팀이 순서(FIFO)·잠금을 직접 바꾸기(명세 13절: 사장 승인).
- 경영팀이 코드·기획서·테스트 결과·법무 판정 고치기(명세 4.5).
- 상태 집계를 AI가 다시 세기(프로그램 값을 그대로 인용, 없으면 "확인된 데이터 없음" — 명세 15절).

## 6. 두 컴퓨터 이어 쓰기 + main 보호 (집 Windows ↔ 밖 Mac, 동시에는 안 씀)

ai-workflow 구현: `session-start.sh`(동기화 점검·훅 경로 연결), `check-tests.sh`(wip 예외), `guard-git.sh`(뒷문), `.githooks/pre-push`(마지막 방어선), GitHub main 브랜치 기본 보호, `/handoff` "다른 컴퓨터로 옮길 때", 시험 `test-hooks.sh`.

가상오피스 **개발 저장소**를 두 컴퓨터에서 쓴다면 그대로 옮긴다(앱 기능이 아니라 개발 환경 쪽).

### 6-1. 세션 시작 동기화 점검
- 원격을 받아(읽기만) 알림: 받을 커밋 / **이 컴퓨터에 안 올린 커밋(푸시 잊음)** / **두 갈래**(→ 아무것도 하기 전에 멈추고 물음) / 다른 컴퓨터가 올린 임시 브랜치 / 커밋 안 한 변경 / 원격 확인 실패 / 지난번 작업 컴퓨터(HANDOFF의 `마지막 작업 컴퓨터:` 줄, 푸시할 때마다 갱신).
- **왜**: 번갈아 쓰는 방식의 진짜 위험은 "푸시 잊음·받기 잊음"으로 생기는 두 갈래다. 다른 컴퓨터는 이쪽에 안 올린 게 있는지 알 길이 없으므로, 각 컴퓨터가 시작할 때 자기 상태를 원격과 비교한다.
- 처음엔 "작업 중 경고(잠금처럼)"를 제안했지만 **동시에 안 쓴다**는 사장 답을 듣고 뺐다 — 쓰지 않는 장치는 만들지 않는다.

### 6-2. 임시 브랜치 `wip/<앱>`에서만 실패 상태 커밋 허용 — 사장 결정
- **무엇**: 구현 중(테스트 실패)이라 커밋이 막혀 다른 컴퓨터로 못 옮기는 문제를, 임시 브랜치에서만 예외로 해결. main은 지금처럼 테스트 통과만. 다시 main으로는 `merge --squash` 뒤 **테스트 통과 커밋**으로만.
- **왜**: 자동 구현 루프 중엔 테스트가 일부 실패한 상태가 정상인데, "실패 상태 커밋 금지"가 옮기기를 막았다. 예외 범위를 브랜치 하나로 좁혀 main의 원칙은 그대로.
- **예외는 아주 좁게**: 명령 전체가 정확히 `git commit -m "…"` 꼴일 때만. 앞에 환경 변수·전역 옵션(`--git-dir`·`-c`), 이어 붙인 명령(`;`·`&&`·`|`·줄바꿈), 브랜치 바꾸는 명령이 섞이면 예외 없음.
  - **왜**: 검사는 "실행 전 브랜치"를 보므로 `git switch main && git commit`처럼 이어 붙이면 main에서 실패 커밋이 됐다.
- **main으로 가는 뒷문 차단**: 그대로 합치기(merge·pull·cherry-pick·rebase·reset로 wip 가져오기), `…:main` 푸시(따옴표로 감싸도), 추적 대상이 main인 wip에서 push, 푸시·추적 설정 바꾸기, main 이름 바꾸기·강제 옮기기·update-ref.
- **기존 빈틈도 발견·수정**: `git`과 `commit`/`push` 사이에 옵션을 끼우면(`git -c x=y push --force`) 커밋 검사·강제 푸시 차단을 **통째로 건너뛰었다**.

### 6-3. 마지막 방어선 — git 자체 `pre-push` 훅 (가장 중요한 교훈)
- **무엇**: main으로 올라가는 커밋은 ① 지금 체크아웃한 커밋 ② 커밋 안 한 변경·앱 안 새 파일 없음 ③ 바뀐 앱마다 테스트를 **실제로 돌려 통과** — 셋 다일 때만 올라간다. 어떤 방법으로 만든 커밋이든. 이상한 앱 이름·경로가 섞이면 거부, 코드가 바뀌었는데 테스트 줄이 없으면 거부(모르면 막기). 세션 시작 때 컴퓨터마다 훅 경로를 자동 연결하고, 훅 끄기(`--no-verify`, 줄여 쓰기·따옴표·셸 확장 포함)·훅 경로 바꾸기는 막는다.
- **왜**: 명령 글자 막기는 별명·refspec 표기·전역 옵션·따옴표·셸 확장으로 **7번 넘게** 뚫렸다. 그래서 "명령이 어떻게 생겼든 main에 들어가는 순간"을 보는 장치가 필요했다.
- **GitHub main 브랜치 기본 보호(사장 결정)**: 강제 푸시·삭제 금지, **관리자도 예외 없음**. "테스트 통과 필수(GitHub Actions + PR)"는 안 켬 — 자동 검사 워크플로를 새로 만들고 `/handoff`를 PR 방식으로 바꿔야 해서 첫 앱 뒤 재판단.
- **가상오피스 앱에 옮길 원칙**: "에이전트가 보낸 명령을 읽어 막기" 위에, **최종 상태 변경 지점(예: QA 통과 → 배포 승인, 상태를 '완료'로 바꾸는 API)**에서 실제 결과물·테스트 결과를 다시 확인하는 서버 측 검사를 둔다.

### 6-4. 옮길 때 절차 (`/handoff`)
- "나갈게/마무리해 줘" → 테스트 통과면 main, 실패면 `wip/<앱>`으로 커밋(명령 하나만)·푸시 → 다른 컴퓨터는 시작 점검이 알려 주면 그 브랜치로 바꿔 이어서 → 다 통과하면 `--squash`로 main에 합치고 로컬 wip 삭제.
- **원격 wip 삭제는 AI가 못 한다**: 보안 훅 완화(브랜치 삭제 허용)를 Claude Code 안전 검사가 막았다 → 사장이 `! git push origin --delete wip/<앱>`. 안 지워도 문제 없음.
- 한 앱에 임시 브랜치 하나, 합치기 전 다른 앱 일 시작 금지.

### 6-5. 따라오지 않는 것 (컴퓨터마다)
`node_modules`·빌드 결과물(잠금 파일로 재설치) / `.env` 비밀값(비밀번호 관리자에서 직접, 절대 커밋 금지) / 실제 업무 견본 파일 / 외부 AI 로그인·API 키 환경 변수 / iOS 빌드는 Mac(Xcode)만.

### 6-6. Mac 호환
- 시험 스크립트의 GNU 전용 `sed -i` → 둘 다 되는 함수(`sed -i.bak` 후 삭제), BSD sed의 `{…;}` 규칙, `\r`은 awk로. 실제 훅은 원래 Mac 대응(날짜 계산 대체, Windows 전용 명령은 없으면 건너뜀).
- **아직 Mac에서 실제로 돌려 본 적 없음** → Mac 준비 때 시험 4종을 한 번 돌려 확인(HANDOFF 3절 7번).

## 9. 적용 순서 (추천)

1. **현재 구조 분석** — 에이전트·팀·상태·잠금·권한이 어디서 정의되는지, 이미 있는 것/빈 곳/해당 없음 대응표 → 사장 검토.
2. **조직·책임표·업무 요청서·답 형식** (1절) — 에이전트 시스템 프롬프트와 화면 설명을 같게.
3. **자원 경계(서버 권한, 기본 거부, 사후 확인)** (2절) — 이후 모든 팀이 이걸 전제로 일함.
4. **법무팀** (3절) — 가장 독립적.
5. **잠금·대기열(DB 기반)** (4절) — 경영팀보다 먼저.
6. **경영팀** (5절) — 요구사항 변경 강제 검사 포함.
7. (개발 저장소를 두 컴퓨터에서 쓰면) **두 컴퓨터 이어 쓰기 + main 보호** (6절).
8. 각 단계: 시험 추가·전부 실행 → 사장 검토 → 커밋. 보안 리뷰 지적은 0절 원칙으로 고친다.
