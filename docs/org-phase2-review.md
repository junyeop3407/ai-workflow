# 조직 개편 2단계 분석 — 법무팀·경영팀 + 병렬·직렬 처리(동시성 제어)

근거: 사장의 "AI 가상오피스 조직 명세"(법무 10절·경영 4절)와 "병렬·직렬 처리 및 동시성 제어 통합 명세서". 분석만 했고 아직 아무것도 바꾸지 않았다. 반영은 사장 검토 뒤.

## 0. 먼저 알아 둘 차이
두 명세서는 **서버·DB·화면이 있는 가상오피스 앱**을 기준으로 썼다(대기열 서버, 서버 재시작 복구, 아바타 상태 표시). 이 작업장(ai-workflow)은 **파일과 스크립트로 도는 작업장**이고, 보통은 **메인 Claude 한 명이 지휘자**라 대부분의 일이 이미 한 줄로 순서대로 흐른다.
그래서 명세서를 그대로 옮기지 않고, **이 작업장에서 실제로 부딪힐 수 있는 곳에만** 같은 원칙(자원 단위 잠금·FIFO·실패해도 안 멈춤·기록)을 건다. 화면 표시(15절)는 `graph.sh status` 한 줄 표시로 대신한다.

## 1. 동시성 — 지금 상태와 빈 곳

### 이미 맞는 것
| 명세서 | 지금 |
|---|---|
| 선행 작업이 끝나야 다음 작업(의존성) | 그래프(`graph.sh`)가 노드 순서를 강제. 표에 없는 다음 노드는 거부 |
| 인수인계(디자인 → 개발) 완료 확인 | ★ok-ui·ok-dd 승인 + 합류(J) 뒤에만 bb 시작 |
| QA 검수는 한 건씩, 정해진 순서 | tr → qa → cx → gm 한 줄. 테스트 결과는 잠금 해시로 고정 |
| 검수 실패 → 고친 뒤 다시 검수, 임의 통과 금지 | 실패 엣지 표 + 개수 확인 + "해결됐어요" 루프 |
| 같은 파일 동시 쓰기 금지(자원 단위) | 그래프 검사가 "동시 노드가 같은 파일을 쓰면" 거부, 개발팀 파일 경계 훅 |
| 작업 기록(감사 로그) | `state.json`의 `log`·`approvals`, `progress.md` |
| 상태 파일이 반쯤 써지는 문제 | 임시 파일에 쓰고 바꿔치기(`mv`) |
| 같은 포트에 서버 두 개 | `backend.sh`가 포트 사용 중이면 멈춤(단, 기다리지 않고 실패) |

### 빈 곳 (실제로 부딪힐 수 있는 곳)
| # | 부딪히는 상황 | 지금 결과 | 명세서 원칙 |
|---|---|---|---|
| A | **세션 두 개**(데스크톱에서 새 세션을 열거나 컴퓨터 두 대)가 같은 앱의 `graph.sh pass/fail`을 거의 동시에 실행 | 둘 다 state.json을 읽고 써서 **한쪽 기록이 사라질 수 있음** | 임계구역 3-1 ④ 공통 상태 변경 |
| B | 두 세션(또는 Stop 훅 + 메인)이 **같은 테스트 환경**(포트 8080, Playwright 서버 포트)을 동시에 씀 | 한쪽이 "포트 사용 중"으로 실패 → 자동 루프가 테스트 실패로 오해 | 3-1 ⑥ 테스트 환경 |
| C | 두 세션이 동시에 **커밋·푸시** | git 잠금 오류 또는 push 거절 | 3-1 ⑨ 최종 병합·배포 |
| D | 앱 두 개를 동시에 만들 때 서로 다른 앱인데도 같은 포트 기본값(8080) | B와 같음 | 3-3 "다른 프로젝트라도 같은 환경이면 잠금" |
| E | 백엔드와 프론트를 **동시에** 개발(명세 9-1: API 규격이 확정되면 병렬) | 지금은 bb → bf 순서로만 | 2-1 병렬 처리 |
| F | 같은 에이전트에게 같은 업무 요청을 두 번 보냄(재시도) | 막는 장치 없음(사람이 보면 알 수 있는 정도) | 12절 멱등성 |

명세서의 나머지(서버 재시작 복구, 대기열 서버, 아바타 표시)는 이 작업장에 해당 없음. state.json이 파일로 남아 있어서 "재시작 후 복구"는 이미 된다.

### 제안: 작은 잠금 도구 하나 (`.claude/hooks/lock.sh`)
전역 잠금 하나가 아니라 **자원 이름별 잠금**:
- `state:<앱>` — graph.sh가 state.json을 고치는 동안(A)
- `env:port:<번호>` — 테스트·서버를 띄우는 동안(B·D). 앱마다 포트를 따로 정해 HANDOFF에 적는 것도 함께
- `git` — 커밋·푸시하는 동안(C)

동작(명세서 10·11절을 파일로):
- **원자적 획득**: 폴더 만들기(`mkdir`)는 동시에 해도 한 명만 성공 → 잠금
- **FIFO**: 번호표(원자적으로 발급)를 받고 앞 번호가 끝나야 내 차례
- **소유자·만료(lease)**: 누가, 언제부터, 몇 초까지. 만료돼도 **그 프로세스가 정말 죽었는지 확인**한 뒤에만 회수
- **세대 번호(fencing token)**: 잠금을 다시 잡을 때마다 번호가 올라감. graph.sh는 쓰기 직전에 "내 번호가 아직 최신인가" 확인 → 늦게 깨어난 옛 작업이 덮어쓰지 못함(명세 11-3)
- **실패해도 풀림**: 스크립트가 실패·중단돼도 trap으로 해제. 오래 잡혀 있으면 graph.sh status에 "잠금 지연" 표시 → 사장 보고(②)
- **기록**: 획득·해제·회수를 `state.json` log에
- 시험: 명세서 17절 중 이 작업장에 맞는 것 — FIFO(1·2), 동시에 하나만(6), 실패 뒤 해제(4), 만료·옛 작업 차단(8), 독립 작업은 안 기다림(3·10), 같은 자원 직렬(11)

E(백엔드∥프론트 병렬)는 별도 선택: 프론트가 api.md 예시로 가짜 응답을 띄워 먼저 짜고, 백엔드가 끝나면 진짜 서버로 승인 테스트. 빨라지지만 그래프를 바꾸고(합류 노드 추가) 사용량이 늘어난다.

## 2. 법무팀 설계안
| 항목 | 제안 |
|---|---|
| 에이전트 | `legal` — 조사는 하되 **코드는 못 고침**. 쓸 수 있는 곳은 `docs/legal.md`뿐(훅). 웹 조사(이용약관·라이선스·robots.txt) 가능 |
| 모델 | `ai-team.md` 기준 "판단" → opus. 드물게 불리므로 비용 부담 작음 |
| 언제 1 — 기획 직후 | 새 노드 `lg`(ok-req 다음, opt 전). 기획서에 새 절 `## 외부 자료·데이터`(출처·쓰는 방식: 내부 참고/화면 표시/AI 학습·RAG/상업 이용)와 개인정보 항목을 적게 하고, 자료마다 GREEN/YELLOW/RED + 조건을 `docs/legal.md`에 |
| 통과 규칙 | RED 0개. YELLOW가 있으면 ★(사장이 "조건부로 진행 / 대체 자료 / 빼기" 고름). 외부 자료도 개인정보도 없으면 자동으로 건너뜀(`법무 해당 없음`) |
| 언제 2 — 출시 전 | sa(보안 감사) 옆에서 한 번 더: 오픈소스 라이선스 고지, 개인정보처리방침·약관이 실제 동작과 맞는지 → 체크리스트 21·22번 추가 |
| 병렬·직렬(명세 6-6) | 출처가 여러 개면 출처별 조사는 동시에(에이전트 여러 개), **최종 판정 `legal.md` 작성은 한 번에 하나**(메인이 합침) |
| 한계 | "법률 자문이 아님"을 보고서에 항상 적고, 위험이 크면 변호사 확인을 권함(명세 10.6) |

## 3. 경영팀 설계안
명세서의 경영팀 일 중 **순서·상태·병목 감지·브레이크는 이미 graph.sh(프로그램)가 한다**. AI가 이걸 다시 하면 중복이고 틀릴 수도 있다. 그래서 경영팀은 **판단이 필요한 순간에만** 부른다.

| 항목 | 제안 |
|---|---|
| 에이전트 | `manager` — 읽기 전용, `docs/ops.md`에만 씀(훅). 순서를 직접 바꾸지 않고 **조정안 + 추천**만 냄 → 사장 승인 → graph.sh가 실행 |
| 부르는 때 ① 요구사항 변경 | ok-qa에서 "요구사항 자체가 틀림·테스트 목록에 없는 요구", 이어 하는 앱에 기능 추가 → 어떤 팀의 어떤 결과물(기획서·테스트·api.md·DESIGN.md·코드)이 영향을 받는지, 다시 돌 노드, 예상 비용 |
| ② 막힘 보고 | 사장 보고(②: 횟수 초과·정체) 때 원인 분석과 보기 2~3개 |
| ③ 잠금 지연 | 1절 잠금이 오래 잡혀 있을 때 원인(죽은 세션인지, 진짜 오래 걸리는지) |
| 할 수 없는 것 | 코드·기획서·테스트 결과·법무 판정 수정, FIFO 순서 임의 변경(명세 13절: 순서 바꾸기는 사장 승인) |

## 4. 추천 진행 순서
1. **법무팀**(가장 독립적, 그래프에 노드 하나 + 에이전트 + 체크리스트 2개)
2. **동시성 잠금 도구**(A·B·C·D) — 경영팀 ③이 이걸 보기 때문에 경영팀보다 먼저
3. **경영팀**(①②③)
4. (선택) 백엔드∥프론트 병렬 개발(E)

각 단계 끝에 시험(test-hooks·test-graph)을 돌리고 사장 검토를 받는다.
